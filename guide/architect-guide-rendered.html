HTML 文档结构与语义

阶段 01

前端起步

先理解浏览器、页面结构、样式系统和 JavaScript 语言模型，形成可独立完成页面和交互的能力。 · 0/5 已掌握

01

为什么学

所有前端框架最终都会生成 HTML。元素层级、语义和可访问性一旦错误，Vue、React 或 CSS 都只能在错误基础上打补丁。

浏览器如何把 HTML 变成页面

浏览器收到 HTML 后，会先进行词法和语法解析，把标签、文本和属性转换成 Token，再构造成一棵 DOM 树。CSS 会形成 CSSOM，两者结合产生渲染树，随后进入布局、绘制和合成。JavaScript 可以读取和修改 DOM，因此 HTML 的结构质量会直接影响样式、交互和性能。

DOCTYPE 不是普通标签，它决定浏览器使用标准模式还是怪异模式。head 负责元信息、资源链接和页面描述，body 负责可见内容。标签嵌套、属性、内容和元素关系，最终都会反映为 DOM 节点的层次关系。

  • HTML 是文档输入，DOM 是浏览器解析后的对象模型。
  • CSSOM 与 DOM 结合后才形成可布局的渲染树。
  • 修改 DOM 可能触发样式计算、布局、绘制和合成。
<!doctype html>
<html lang="zh-CN">
  <head>
    <meta charset="UTF-8" />
    <meta name="viewport" content="width=device-width, initial-scale=1" />
    <title>巡检任务</title>
  </head>
  <body>
    <main aria-labelledby="page-title">
      <h1 id="page-title">巡检任务</h1>
    </main>
  </body>
</html>

语义化不是装饰，而是接口

语义化标签表达内容职责：header 表示页头，nav 表示导航，main 表示页面唯一主要内容区，section 表示有主题的区块，article 表示可以独立成立的内容，aside 表示补充内容，footer 表示页脚。浏览器、搜索引擎、屏幕阅读器和团队开发者都依赖这些含义理解页面。

标题层级同样属于结构。一个页面通常只应有一个 h1，后续标题按内容层级使用 h2、h3，不能为了字号大小跳级。按钮、链接、表单和图片也需要使用正确元素，而不是给 div 随意绑定点击事件。

  • 先根据内容职责选择标签，再根据设计系统决定外观。
  • 交互控件优先使用原生 button、a、input 和 select。
  • 所有图片都需要判断是内容图片还是装饰图片。

无障碍与可读结构

可访问性从正确 HTML 开始。表单控件需要可访问名称，图片需要合适的替代文本，交互操作需要键盘支持，焦点顺序要符合视觉顺序。ARIA 只在原生语义不足时补充，不能用来修复错误结构。

结构清晰的页面更容易测试和维护。对全栈开发者而言，HTML 是接口契约的起点：它连接浏览器、辅助技术、样式系统和后续框架组件。

  • label 与输入控件要正确关联。
  • 不要用占位符代替标签。
  • 不要移除浏览器默认焦点样式而不提供替代方案。

学习目标

  • 能解释 HTML 解析、DOM 和渲染树的基本关系。
  • 能根据内容职责选择合适的语义元素。
  • 能编写键盘可操作、结构可检查的基础页面。

实践验收

手写一个包含页头、导航、主内容、侧栏、文章和页脚的语义化页面，并为其添加移动端样式和基础无障碍属性。

  • 页面只有一个 main 和一个 h1。
  • 所有表单控件都有可访问名称。
  • 只用键盘就能完成主要导航和交互。

常见误区

  • 把所有内容都用 div 表示。
  • 根据视觉大小错误选择标题层级。
  • 用 ARIA 属性掩盖错误的原生语义。

全栈架构师视角

架构师需要理解 HTML 是跨端输出的基础契约。Web、移动端 WebView、SEO 页面和可访问性能力都共享这套结构。结构稳定后，组件库、设计系统和自动化测试才有可靠基础。

02

为什么学

前端界面的质量很大一部分取决于 CSS 结构。布局、状态和响应式混乱会持续消耗团队时间，也会让组件库无法稳定复用。

层叠、继承与优先级

CSS 的冲突解决不是简单比选择器长短。样式来源、!important、层叠层、作用域、优先级和源码顺序都会参与计算。继承只发生在部分属性上，很多属性不会自动从父元素传给子元素。

当样式频繁使用 !important、深层后代选择器或全局覆盖时，代码会变成互相抢权。合理做法是按基础层、组件层、业务层和工具层组织样式，并保持选择器短而明确。

  • 先看来源和层叠顺序，再看具体性和源码顺序。
  • 避免用 !important 解决结构问题。
  • 组件样式应控制自己的边界，减少向外影响。

盒模型与现代布局

元素尺寸由内容、内边距、边框和外边距共同决定。border-box 让 width 包含边框和内边距，通常更适合组件布局。普通流负责页面基本排列，Flex 适合一维排列，Grid 适合二维轨道，定位适合浮层和少量脱离普通流的结构。

响应式设计不是只加几个媒体查询，而是让内容在最小屏幕到超宽屏幕之间自然重排。断点应由内容开始拥挤的位置决定，而不是机械照搬设备型号。

  • 优先使用 Flex 和 Grid 表达布局关系。
  • 为固定格式组件定义稳定尺寸和最小宽度。
  • 避免用固定高度锁死动态内容。
.page {
  display: grid;
  grid-template-columns: 240px minmax(0, 1fr);
  gap: 24px;
}

@media (max-width: 720px) {
  .page {
    grid-template-columns: 1fr;
  }
}

设计令牌与主题

颜色、间距、字体、圆角、阴影和状态应该被抽象为设计令牌。令牌把视觉规则从组件实现中抽离，使暗色模式、多品牌和一致性调整不需要逐个修改组件。

好的 CSS 架构不仅关注当前页面，还关注状态复用和可维护性。悬停、聚焦、禁用、加载、错误、空状态和移动端排列都应该在组件设计阶段考虑。

  • 使用语义令牌而不是具体颜色名组织主题。
  • 颜色不能单独表达状态，要配合文字或图形。
  • 关键控件在窄屏下必须保持可点击尺寸。

学习目标

  • 能解释 CSS 层叠、继承和盒模型。
  • 能使用 Flex 或 Grid 完成响应式布局。
  • 能建立基础设计令牌和组件样式边界。

实践验收

实现一个包含侧栏、导航、数据表格和移动端抽屉的后台页面，并设计 light/dark 主题令牌。

  • 320px 到宽屏均不出现内容重叠或横向溢出。
  • 交互状态和焦点状态清晰可见。
  • 组件样式不会依赖偶然的父级选择器。

常见误区

  • 依赖 !important 处理所有样式冲突。
  • 使用绝对定位拼装普通页面布局。
  • 只考虑静态状态，忽略加载、错误和空状态。

全栈架构师视角

设计系统是架构的一部分。架构师需要把视觉令牌、组件边界、响应式策略和无障碍要求沉淀为可执行规范，而不是只交付一套看起来不错的页面。

03

为什么学

Vue、React、Node 和任何前端工具都建立在 JavaScript 语言模型上。语言基础不牢，框架问题最终会表现为状态不可解释、异步失控和错误难以恢复。

作用域、闭包与 this

JavaScript 使用词法作用域，函数在定义时就能访问外层变量。闭包是函数与其定义环境的组合，它使内部状态在函数执行结束后仍然可以保留。防抖、节流、缓存、Hook 和模块封装都依赖闭包。

this 取决于调用方式，而不是函数定义位置。普通调用、对象方法、call/apply、new 和箭头函数有不同的绑定规则。箭头函数没有自己的 this，适合沿用外层上下文。

  • 闭包捕获的是作用域中的变量绑定，不是某个瞬间的复制值。
  • 异步回调中的变量值要在回调真正执行时判断。
  • 能用普通参数和显式上下文，就不要依赖隐式 this。
function createCounter() {
  let count = 0
  return () => {
    count += 1
    return count
  }
}

const next = createCounter()
console.log(next()) // 1
console.log(next()) // 2

对象、原型与数据转换

JavaScript 对象通过原型链查找属性。class 是原型继承的语法糖，理解原型有助于阅读库源码和分析方法来源。对象、数组、Map 和 Set 提供不同的数据访问和迭代能力。

业务代码大量时间花在数据转换。浅拷贝和深拷贝、可变与不可变、排序稳定性、稀疏数组和引用共享都会影响状态更新。应在业务边界使用明确的数据结构，而不是把任意对象层层传递。

  • 先判断数据需要按顺序访问、按键访问还是去重访问。
  • 浅拷贝只复制第一层引用。
  • 状态更新要避免意外修改共享对象。

异步、模块和异常

Promise 把异步结果统一成可组合对象，async/await 让异步流程更接近同步阅读方式，但底层仍然是事件循环调度。并发控制、超时、取消和部分失败处理不能靠 await 关键字自动完成。

模块把代码切成有明确入口和依赖边界的小单元。错误则必须跨越同步、异步和模块边界传播到可处理的层级。生产中不能只 console.log 错误，也不能让 Promise 拒绝无人处理。

  • Promise.all 用于全部成功，Promise.allSettled 用于保留部分结果。
  • 取消需要把信号传到真正执行 I/O 的位置。
  • catch 必须保留上下文或转换成明确业务错误。

学习目标

  • 能解释闭包、this、原型链和事件循环的基本行为。
  • 能正确处理并发、取消、错误和模块依赖。
  • 能为数据结构选择合适操作并控制引用变化。

实践验收

实现一个支持并发限制、超时、取消、重试和部分成功的请求工具，并为关键函数编写测试。

  • 能解释任意回调中的变量值和 this 来源。
  • 未处理的 Promise 拒绝不会静默消失。
  • 模块之间没有隐式全局共享状态。

常见误区

  • 把 async 函数理解为真正并行执行。
  • catch 后什么都不做或重复抛出失去上下文。
  • 用深拷贝解决所有状态共享问题。

全栈架构师视角

架构师需要理解执行模型和错误边界。系统中真正的稳定性来自明确的状态生命周期、可取消的异步操作和可追踪的错误传播，而不是堆叠更多框架。

04

为什么学

很多所谓框架问题其实是浏览器问题：为什么请求重复、为什么事件失效、为什么页面卡顿、为什么用户退出后数据还在。理解浏览器才能定位根因。

DOM、事件和渲染管线

DOM 是浏览器对文档的对象表示。JavaScript 修改 DOM 后，浏览器会重新计算样式、布局、绘制并合成，但并非每次修改都会同步完成所有工作。读取布局属性可能强制浏览器提前计算，形成布局抖动。

事件在捕获、目标、冒泡阶段传播。事件委托利用冒泡把多个子元素事件集中处理。异步事件中的状态可能已经变化，因此事件处理必须结合状态来源和清理逻辑。

  • 先批量更新 DOM，再统一读取布局信息。
  • 事件监听器必须在组件销毁或页面切换时清理。
  • 键盘事件和指针事件要共同设计。

HTTP 请求和浏览器缓存

浏览器通过 HTTP 方法、状态码、响应头和缓存策略与服务器交互。GET 通常用于读取，POST 用于创建，PUT/PATCH 用于更新，DELETE 用于删除。状态码表达请求结果，业务错误也应使用稳定的响应结构。

缓存由 Cache-Control、ETag、Last-Modified、Vary 等头共同决定。缓存能提升性能，但必须考虑用户身份、权限和实时性。前端私有数据不能与公共资源共享同一缓存键。

  • 区分网络失败、超时、权限失败和业务失败。
  • 凭证、Cookie 和跨域策略必须在真实域名下验证。
  • 缓存策略要同时考虑性能和数据新鲜度。

浏览器存储与安全边界

Cookie、localStorage、sessionStorage 和 IndexedDB 的容量、生命周期和安全模型不同。Cookie 会随请求发送，适合会话凭证但要考虑 CSRF；localStorage 简单但同步并且容易被 XSS 读取；IndexedDB 适合结构化离线数据但使用复杂。

前端存储不能作为安全边界。敏感数据应由服务端权限控制并尽量少存。任何来自 URL、存储、消息或第三方脚本的数据都必须被视为不可信输入。

  • 不要把长期敏感 Token 放在无保护的前端存储中。
  • 跨标签页通信要验证消息来源。
  • 离线数据需要版本、迁移和冲突策略。

学习目标

  • 能解释页面从 HTML 到可见内容的流程。
  • 能设计可靠的事件、请求和错误状态。
  • 能根据生命周期和安全需求选择浏览器存储。

实践验收

实现一个带取消、重试、缓存、离线状态、键盘操作和跨标签页同步的任务列表。

  • 重复请求和快速切换不会写入过期结果。
  • 事件监听器和定时器没有泄漏。
  • 权限变更后不会继续展示旧数据。

常见误区

  • 认为 fetch 返回成功就一定业务成功。
  • 把 localStorage 当作安全存储。
  • 只监听 click 忽略键盘和触摸输入。

全栈架构师视角

架构师需要从浏览器边界思考数据流和安全。缓存、登录、权限、离线、跨标签同步和多端行为都需要明确契约，否则前后端各自实现一套后会产生难以定位的状态冲突。

05

为什么学

从个人项目进入团队协作后，工作区是否干净、依赖是否可重现、问题是否可复现，直接决定协作成本。

Git 是协作时间线

Git 的工作区、暂存区和提交区形成可审查的变更流程。提交应表达单一意图，提交正文说明背景、关键改动和验证结果。分支、合并和变基都只是组织历史的手段，不是目的。

出现冲突时要理解双方变更的业务意图，不能机械选择当前分支或传入分支。回滚也应优先使用可审计的反向提交，避免重写已经共享的历史。

  • 提交前阅读 diff，确认没有无关格式化和敏感信息。
  • 一个提交只解决一个清晰问题。
  • 不要把生成物、Secret 和本地配置提交进仓库。
git status
git diff
git add src/example.ts
git diff --cached
git commit -m "feat: 增加任务筛选"

包管理、依赖边界和可重现

包管理器通过清单和锁文件记录直接依赖、间接依赖和版本解析结果。团队必须统一包管理器，根目录维护锁文件，子包不单独生成锁文件。依赖升级要评估破坏性变更、许可证和安全风险。

workspace 通过包边界共享代码。公共包只暴露必要入口，业务包不能依赖另一个包的内部文件。清晰的依赖方向能减少循环依赖和构建影响范围。

  • 生产依赖和开发依赖要明确区分。
  • 锁文件必须进入版本控制并在 CI 使用。
  • 共享包不能成为所有代码的垃圾桶。

调试、格式和静态检查

调试不是随机修改代码，而是先复现，再缩小范围，最后验证根因。浏览器 Network、Sources、Performance、Application 和 Node 调试器分别覆盖不同层的问题。日志要带关联 ID，错误要保留堆栈和上下文。

格式化、Lint 和类型检查负责机械质量，代码审查负责业务语义、权限、边界和可维护性。自动化工具越稳定，人工评审越能关注真正重要的设计问题。

  • 先构造最小复现，再修改实现。
  • 本地和 CI 使用同一套检查规则。
  • 不要通过关闭规则来掩盖设计问题。

学习目标

  • 能使用 Git 表达清晰、可审查的变更。
  • 能维护统一的依赖图和锁文件。
  • 能通过工具和日志系统性定位问题。

实践验收

建立一个带提交检查、格式、Lint、类型检查、基础测试和本地调试配置的最小项目。

  • 新环境能按文档重现安装和运行。
  • 每次提交都能说明目的和验证方式。
  • 常见错误能通过日志或复现步骤定位。

常见误区

  • 用 commit --amend 修改已经被他人使用过的历史。
  • 在不同目录混用 npm、yarn 和 pnpm。
  • 格式化失败后随意扩大改动范围。

全栈架构师视角

架构师需要关注工程系统的可恢复性。版本、依赖、构建、检查、发布和回滚都应可追溯。没有这些基础，再好的架构也无法稳定演进。

前端应用与工程

06

为什么学

应用规模变大后，真正昂贵的不是写类型，而是误改接口、遗漏状态分支和无法判断数据是否可靠。类型系统能把这些风险提前暴露。

推断、注解与对象建模

TypeScript 会从初始化和上下文自动推断大部分类型，开发者只需要在公共边界、复杂逻辑和无法推断的位置补充注解。接口、类型别名和对象类型可以描述 API、组件 Props、领域实体和配置结构。

可选字段不等于字段一定存在。大量可选字段往往表示状态没有被正确建模。只读字段、精确字面量和判别字段可以把非法数据提前排除，让调用方在编码阶段就看到约束。

  • 优先让类型从实现和 Schema 推导。
  • 公共 API 的输入输出应稳定且可读。
  • 避免用 any 绕过问题，必要时用 unknown 后再收窄。
type TaskState =
  | { status: "idle" }
  | { status: "loading" }
  | { status: "success"; data: Task[] }
  | { status: "error"; message: string }

function render(state: TaskState) {
  if (state.status === "success") return state.data.length
  if (state.status === "error") return state.message
  return 0
}

泛型、组合与重构

泛型的价值是保留输入和输出之间的类型关系。工具函数、API 客户端、状态容器和事件总线都可能需要泛型，但泛型参数应由调用位置自然推断，而不是强迫调用方重复写类型。

类型组合可以从领域模型派生创建、更新、查询和展示类型。随着接口变化，编译器会指出所有受影响位置。高级条件类型和映射类型适合公共库和适配层，普通业务代码应以可读性为先。

  • 泛型参数必须有明确约束和真实复用价值。
  • 从单一事实来源派生类型，减少重复声明。
  • 类型报错应能定位到业务边界，而不是隐藏在复杂类型内部。

类型边界与运行时校验

TypeScript 类型在运行时不存在。网络响应、环境变量、URL 参数、数据库结果和第三方 SDK 都可能与声明不符。因此外部数据进入系统时必须做运行时校验，再由 Schema 推导静态类型。

类型系统不能替代业务校验。类型只回答结构是否可能合法，业务规则还需要判断权限、状态、范围和组合条件。前端校验用于体验，服务端校验才是最终约束。

  • 外部输入先在边界校验，再进入业务逻辑。
  • 运行时 Schema 和静态类型尽量来自同一来源。
  • 错误信息要能帮助调用方修正输入。
const TaskSchema = z.object({
  id: z.string(),
  title: z.string().min(1),
  status: z.enum(["todo", "doing", "done"]),
})

type Task = z.infer<typeof TaskSchema>

学习目标

  • 能用联合类型表达互斥状态并做穷尽检查。
  • 能设计可读的泛型和组合类型。
  • 能把运行时校验与静态类型连接起来。

实践验收

为一个 API 客户端和环境配置建立运行时 Schema，并从 Schema 推导 TypeScript 类型。

  • 外部数据未经校验不会进入业务逻辑。
  • 状态分支能被编译器检查出遗漏。
  • 调用公共工具时不需要重复书写类型参数。

常见误区

  • 用 as 强制转换外部响应。
  • 用大量可选字段掩盖状态设计问题。
  • 为了炫技引入难以阅读的高级类型。

全栈架构师视角

类型系统是跨团队契约的一部分。架构师需要决定哪些边界使用代码生成、共享 Schema 和统一错误类型，从而让前端、Node 和服务端对同一业务概念保持一致理解。

07

为什么学

Vue 容易上手，但大型项目的问题通常不是指令不会用，而是状态归属不清、组件职责混乱、请求和路由状态不可恢复。

响应式与组件数据流

Vue 会跟踪响应式数据在渲染和计算过程中的读取，并在数据变化时触发相关更新。ref 适合基础值和需要整体替换的对象，reactive 适合嵌套对象，但解构和替换会破坏响应关系。

组件通过 Props 接收数据、通过 Emits 通知父组件、通过 Slots 接收结构扩展。单向数据流让数据来源明确，也便于调试。父组件提供的对象不能在子组件中被随意原地修改。

  • 派生值优先使用 computed，不要在模板中重复计算。
  • 组件通信方式要与组件关系匹配。
  • 状态更新来源越集中，越容易追踪。
<script setup lang="ts">
const props = defineProps<{ count: number }>()
const emit = defineEmits<{ change: [value: number] }>()
</script>

<template>
  <button type="button" @click="emit('change', props.count + 1)">
    {{ count }}
  </button>
</template>

组合函数与状态边界

Composition API 的价值是把数据获取、分页、权限、表单和副作用组织成可测试的组合函数。组合函数应有清晰的输入输出，并在组件卸载时清理订阅、定时器和请求。

Pinia 适合跨页面共享的用户、权限、项目上下文和通知，不应把所有局部状态都塞进 store。URL 适合筛选、分页和详情标识，组件局部状态适合弹窗、输入草稿和临时选择。

  • 先判断状态属于组件、URL 还是全局。
  • 服务端数据需要缓存和失效策略，不能简单复制到 store。
  • 组合函数只暴露调用方真正需要的能力。

路由、请求和错误状态

路由负责页面组织、权限守卫和 URL 状态。动态路由、查询参数、嵌套路由和懒加载共同影响页面恢复、刷新和权限行为。路由守卫应处理身份和访问控制，但服务端仍然必须再次授权。

请求状态需要统一管理加载、成功、空、错误和取消。组件不应在多个生命周期中各自发起重复请求。表单提交要有校验、防重、服务端错误回显和成功后的状态同步。

  • 关键页面状态应能通过 URL 恢复。
  • 请求取消要传到真实数据源。
  • 错误提示要区分网络、权限、校验和未知错误。

学习目标

  • 能解释响应式依赖和组件数据流。
  • 能拆分可复用组合函数并管理服务端状态。
  • 能设计可恢复的路由和请求错误状态。

实践验收

实现一个包含列表、筛选、分页、详情、编辑、权限路由和错误恢复的 Vue 后台模块。

  • 刷新页面后筛选和分页状态仍能恢复。
  • 快速切换页面不会写入过期请求结果。
  • 核心逻辑通过组合函数或独立模块测试。

常见误区

  • 用事件总线处理所有跨组件通信。
  • 把所有数据都放进 Pinia。
  • 依赖前端路由守卫代替服务端授权。

全栈架构师视角

框架选择不是架构终点。架构师需要定义前后端契约、错误模型、数据缓存策略和权限边界，让 Vue 只负责稳定消费这些能力。

08

为什么学

React 的自由度很高，小项目可以快速迭代，大项目如果没有状态和数据边界，很容易形成难以追踪的重渲染、重复请求和循环依赖。

状态、派生值和渲染

React 组件在状态或 props 变化时重新执行并生成新的元素树。可计算的数据应作为派生值，而不是重复放入 state。动态列表需要稳定 key，否则组件身份会错误复用。

状态应尽量靠近使用位置。只有当多个组件需要同步读取和更新时才提升状态或引入共享状态。全局状态越多，组件复用和测试越困难。

  • 能推导出的值不要重复存 state。
  • 状态更新要基于前一个状态时使用函数式更新。
  • 组件身份应由业务 ID 而不是数组索引决定。
function Counter() {
  const [count, setCount] = useState(0)
  const doubled = count * 2

  return (
    <button onClick={() => setCount((value) => value + 1)}>
      {count} / {doubled}
    </button>
  )
}

Hooks 与副作用边界

Hook 只能在组件或自定义 Hook 顶层调用，因为 React 依赖调用顺序匹配状态。useEffect 用于同步外部系统，如订阅、计时器和 DOM API。数据请求通常更适合服务端状态库，而不是在每个页面手写 useEffect。

每个副作用都要设计清理逻辑。依赖数组不是装饰，它描述副作用读取了哪些外部值。忽略依赖会造成闭包旧值，依赖过多可能表示逻辑没有拆开。

  • 副作用必须成对设计注册和清理。
  • 不要为了“只执行一次”而忽略真实依赖。
  • 自定义 Hook 要有明确单一职责。

服务端状态与大型应用架构

服务端数据与客户端 UI 状态生命周期不同。服务端状态需要缓存、失效、重试、预取和并发控制，客户端状态关注弹窗、输入、布局和选择。把它们混在一起会导致重复请求和状态冲突。

大型 React 应用应按业务能力组织模块，而不是只按组件、Hook、服务和工具类型分目录。模块只暴露公共入口，依赖方向稳定，跨模块能力通过明确接口传递。

  • 请求缓存使用稳定的 query key。
  • 缓存失效策略要基于业务写入行为。
  • 模块边界优先于文件夹命名形式。

学习目标

  • 能区分客户端状态和服务端状态。
  • 能正确使用 Hooks 并设计清理逻辑。
  • 能按业务模块组织大型 React 应用。

实践验收

实现一个带权限、列表缓存、详情预取、表单编辑、错误边界和性能分析的 React 后台模块。

  • 切换路由不会重复请求已有数据。
  • 副作用的注册和清理行为可测试。
  • 模块之间不存在隐式全局依赖和循环引用。

常见误区

  • 把 useEffect 当作所有逻辑的入口。
  • 无脑 memo 所有组件。
  • 全局 Context 频繁更新导致整棵组件树重渲染。

全栈架构师视角

React 生态会不断变化，但状态归属、缓存一致性和模块边界是稳定问题。架构师应制定这些规则，而不是追逐每一个新 Hook 或新框架 API。

09

为什么学

前端应用的复杂度主要来自状态生命周期。状态归属、缓存和权限一旦混乱，页面会表现为随机旧数据、重复请求和操作不可预测。

先决定状态归属

筛选、分页、排序和详情 ID 应该进入 URL，因为用户需要刷新恢复、分享和前进后退。弹窗、拖拽、临时选中适合组件局部状态。用户、权限和跨页面通知适合全局状态。服务端数据应由专门的数据层管理。

状态归属错误会产生同步问题。例如把分页同时放在 URL、store 和组件中，任何一处更新都需要手动同步其他两处。正确做法是选择一个权威来源，其他位置只读取或派生。

  • 刷新后必须恢复的状态优先放 URL。
  • 服务端数据不复制成多个长期状态副本。
  • 一个概念只设置一个权威来源。

缓存、请求和一致性

服务端缓存需要稳定缓存键，键应包含用户、租户、资源和筛选条件。写入成功后要主动失效或更新相关缓存。乐观更新适合低风险操作，但失败时必须回滚并提示用户。

并发请求要处理竞态：旧请求可能比新请求更晚返回。取消请求、版本号或请求标识都能避免旧结果覆盖新状态。

  • 缓存键必须表达数据身份。
  • 写操作成功后明确要失效哪些查询。
  • 快速筛选和切换页面要防止旧响应覆盖新响应。

表单与权限状态

表单需要初始值、草稿、校验、提交中、服务端错误、成功和重置状态。复杂表单应把字段规则、依赖关系和跨字段校验集中管理，避免散落在模板中。

权限状态来源必须可追踪。前端根据权限隐藏或禁用操作只是体验优化，服务端仍需再次授权。权限变化后，前端缓存和路由也需要更新，避免展示已经不可访问的数据。

  • 服务端字段错误要映射到具体控件。
  • 提交中要防重，并允许用户理解当前进度。
  • 权限变化应触发缓存和路由重新校验。

学习目标

  • 能根据生命周期选择 URL、局部、全局或服务端状态。
  • 能设计缓存键、失效和并发处理。
  • 能处理复杂表单和权限变化。

实践验收

实现一个可分享筛选、支持缓存和详情预取、包含复杂表单和权限变化的后台模块。

  • 刷新、后退和分享链接都能恢复正确状态。
  • 写入后相关页面不会显示旧数据。
  • 权限变化后不可访问数据会被清除。

常见误区

  • 把所有状态都放进全局 store。
  • 在多个位置维护同一份分页状态。
  • 写入成功却不失效相关缓存。

全栈架构师视角

架构师需要统一前端的数据契约和缓存模型。哪些数据可缓存、缓存多久、写入后如何失效、权限变化如何清理，都应由跨团队规则决定。

10

为什么学

前端进入多人协作和生产发布后，最大的成本不是写组件，而是回归、构建失败、性能退化和跨端不一致。

构建与交付

开发服务器负责快速反馈，生产构建负责转译、打包、压缩、代码分割和资源指纹。开发和生产行为不同，必须在接近生产的环境中验证。构建产物要能分析体积、依赖和加载路径。

按路由和大型组件拆包，延迟加载非关键功能。第三方依赖要检查是否有浏览器兼容性和体积成本。环境变量只能提供构建时配置，敏感配置必须留在服务端。

  • 首屏只加载必要代码和数据。
  • 构建产物可重复且能追踪版本。
  • 浏览器专用和服务端专用代码不能互相污染。

测试金字塔与质量门禁

单元测试验证纯逻辑，组件测试验证交互和状态，集成测试验证模块协作，端到端测试覆盖关键用户流程。测试应覆盖风险和业务规则，而不是追求形式覆盖率。

质量门禁包括格式、Lint、类型、测试和构建。它们在 Pull Request 和主分支持续执行。失败时先修复根因，不通过关闭规则绕过。

  • 测试名描述用户或系统行为。
  • 测试数据独立且可重复。
  • 关键权限和错误路径必须有测试。

性能和无障碍作为质量属性

性能关注加载、渲染、交互和网络。先用浏览器性能工具测量，再优化真实瓶颈。常见手段包括减少阻塞资源、控制包体积、虚拟列表、缓存、图片优化和减少布局抖动。

无障碍需要语义、键盘、焦点、对比度和动态内容通知。性能优化不能牺牲可访问性，例如删除焦点样式或把内容渲染到不可访问的 canvas 中。

  • 为关键页面建立性能预算。
  • 键盘和屏幕阅读器流程纳入验收。
  • 优化前后保留数据和证据。

学习目标

  • 能设计构建、测试和质量门禁。
  • 能使用真实数据定位前端性能问题。
  • 能把无障碍和性能纳入交付标准。

实践验收

为一个中型前端项目配置 CI、测试层次、产物分析和性能预算，并完成一次无障碍审查。

  • 主分支始终可构建并可通过质量门禁。
  • 关键页面有性能基线和回归证据。
  • 主要流程只用键盘即可完成。

常见误区

  • 只跑端到端测试覆盖所有分支。
  • 依赖本地感觉判断性能。
  • 把无障碍留到上线前补做。

全栈架构师视角

架构师需要把质量属性变成自动化和可度量的标准。构建、测试、性能和可访问性不是个人技巧，而是团队交付能力的一部分。

服务端与数据

进入 Node、HTTP、接口、认证授权、SQL、事务、索引、缓存、队列和可观测性，打通完整业务链路。 · 0/7 已掌握

11

为什么学

从浏览器进入服务端后，代码不再只服务一个用户。并发、资源、进程生命周期和外部依赖可靠性会直接决定系统稳定性。

事件循环和异步 I/O

Node 主线程执行 JavaScript，文件、网络和 DNS 等 I/O 由底层线程池或操作系统异步完成。回调、Promise 微任务和不同事件循环阶段决定任务何时执行。CPU 密集的同步代码会阻塞所有请求。

并发并不等于多线程执行 JavaScript。Node 通过非阻塞 I/O 和事件循环提高资源利用率。需要 CPU 密集处理时，应拆分任务、使用 Worker Threads 或独立服务。

  • 避免在请求路径执行长同步循环和大规模 JSON 处理。
  • Promise 拒绝必须有明确处理位置。
  • 并发上限要为数据库和下游服务留出余量。
const results = await Promise.all(
  ids.map((id) =>
    Promise.race([
      fetchTask(id),
      new Promise((_, reject) =>
        setTimeout(() => reject(new Error("timeout")), 3000),
      ),
    ]),
  ),
)

模块、HTTP Server 和流

Node 支持 CommonJS 和 ESM，模块解析受 package.json、exports 和文件扩展名影响。服务入口通常创建 HTTP Server，再由 Express、Fastify 或 NestJS 接管请求。框架之外仍需理解端口、连接、请求超时和响应关闭。

Stream 适合处理大文件、日志、上传、下载和实时响应。流必须处理背压：生产速度快于消费速度时，要等待 drain 或使用 pipe。客户端断开后要停止后续写入并释放资源。

  • 公共包通过 exports 暴露稳定入口。
  • 大文件不能全部读入内存。
  • 流、数据库连接和子进程都需要显式释放。

环境、进程和优雅停机

配置应在启动阶段校验，缺失或非法时立即退出，避免服务半可用。Secret 通过环境、Secret Manager 或挂载文件提供，不进入仓库和日志。

收到 SIGTERM 或 SIGINT 后，服务应先停止接收新请求，等待在途请求完成，关闭数据库和队列连接，再退出。超过超时时间仍未完成时可以强制退出，但必须保留审计。

  • 启动失败比运行时随机失败更容易定位。
  • 停机过程要区分请求、任务和后台连接。
  • 进程退出码要反映成功或失败。

学习目标

  • 能解释阻塞、并发、事件循环和资源释放。
  • 能组织模块、HTTP 服务和流式处理。
  • 能实现配置校验和优雅停机。

实践验收

实现一个支持 JSON API、文件流下载、结构化日志、配置校验和优雅停机的 Node 服务。

  • 长耗时 CPU 任务不会阻塞健康检查。
  • 客户端断开后文件流和数据库连接被释放。
  • 收到 SIGTERM 后不再接收新请求并安全退出。

常见误区

  • 收到信号立即 process.exit，丢掉在途写入。
  • 把大文件全部读入内存。
  • 使用无上限并发请求数据库。

全栈架构师视角

架构师需要理解服务的运行边界：单实例能承受多少连接、哪些任务应异步、哪些状态不能放进程内存、发布时如何安全替换实例。

为什么学

前端应用的稳定性很大程度取决于接口质量。契约不清会导致前后端反复猜测，错误模型混乱会让用户无法理解失败原因。

HTTP 语义和资源设计

HTTP 方法表达操作意图，状态码表达请求结果。GET 用于读取且应可缓存，POST 用于创建，PUT/PATCH 用于更新，DELETE 用于删除。业务错误不应统一返回 200，否则客户端和网关无法正确判断。

资源路径表达业务实体，查询参数表达筛选、排序和分页。响应结构统一包含数据、错误和可追踪信息。字段命名、日期格式、空值语义和错误码必须跨服务一致。

  • 状态码语义准确。
  • 错误结构稳定且带业务错误码。
  • 分页、排序和筛选规则统一。
{
  "code": "TASK_NOT_FOUND",
  "message": "任务不存在",
  "requestId": "01J...",
  "details": []
}

参数校验和错误模型

路径参数、查询参数、请求体、文件元数据和外部响应都要校验。校验分为结构校验、业务校验和权限校验。结构校验可以在 Controller 边界完成，业务规则放到 Service，资源权限必须有最终服务端检查。

错误应区分客户端可修复、权限问题、资源冲突、上游失败和内部异常。验证错误返回字段级信息；未知异常只记录内部堆栈，对客户端返回稳定错误码和 requestId。

  • 错误码是接口契约，不随意改名。
  • 不要在错误响应泄露 SQL、堆栈和内部路径。
  • 校验失败要给出可操作的字段信息。

版本、幂等和契约测试

接口变更应优先向后兼容。新增可选字段风险较低，删除字段、改变含义和改变状态码需要版本策略。客户端和服务端应基于 OpenAPI 或共享 Schema 验证契约。

网络超时不能证明写操作没有成功。创建任务、支付、发送通知等操作需要幂等键，重复请求返回同一业务结果。契约测试验证双方是否仍按约定理解和返回数据。

  • 写操作明确幂等策略。
  • 接口文档从代码或 Schema 生成。
  • 破坏性变更提供迁移窗口。

学习目标

  • 能设计资源、状态码、分页和错误响应。
  • 能分层处理结构、业务和权限校验。
  • 能为写操作设计幂等和兼容演进。

实践验收

为一个任务平台设计完整 API 契约，并使用 Schema 生成类型、校验请求和编写契约测试。

  • 所有错误都有稳定错误码和 requestId。
  • 重复提交同一幂等键不会产生重复业务结果。
  • 客户端可以从契约生成类型而不是手写猜测。

常见误区

  • 所有错误都返回 200 和一段字符串。
  • 把数据库行结构直接暴露为 API。
  • 无版本策略随意删除字段。

全栈架构师视角

架构师要维护跨团队契约。接口不只是函数调用，它连接前端、Node、数据库、测试、文档和外部系统，任何变更都要考虑依赖影响。

为什么学

权限漏洞的代价远高于普通功能缺陷。Agent、自动化和后台任务都需要明确身份和授权边界，不能因为“内部系统”就降低安全要求。

认证机制和 Token 生命周期

Session 适合由服务端保存会话状态，JWT 适合无状态校验但撤销更复杂。OAuth2 关注授权委托。Token 通常有访问令牌、刷新令牌、过期时间和撤销机制，必须安全存储和传输。

前端不应把长期 Token 放入容易受到 XSS 攻击的位置。服务端不能记录完整 Token、密码或密钥。刷新失败、退出登录和权限变化都要清理本地缓存。

  • 访问 Token 短期、刷新 Token 长期并限制使用。
  • Token 不进入日志、URL 和 Prompt。
  • 退出登录需要服务端撤销或版本失效。

RBAC、ABAC 与资源归属

RBAC 按角色授予能力，ABAC 结合用户、资源、环境和动作属性判断。真实系统通常组合使用：角色决定基础权限，资源归属和状态决定是否允许当前动作。

项目负责人、项目成员、任务负责人和访客可能拥有不同操作。权限校验必须发生在服务端资源层，不能仅依赖前端隐藏按钮。

  • 权限规则集中、可测试、可审计。
  • 资源 ID 不能作为访问权限证明。
  • 删除、导出和批量操作是高风险权限。

审计、敏感数据和最小权限

认证和授权失败必须记录关键上下文，但不能记录敏感值。高风险操作需要记录操作人、时间、资源、动作、结果和追踪 ID。日志应脱敏并设置保留期限。

服务账号和后台任务也遵循最小权限。跨租户读取、临时调试权限和导出能力需要额外审批和过期机制。

  • 默认拒绝，按需授予。
  • 权限拒绝返回稳定错误码。
  • 审计记录用于追溯而不是收集更多个人信息。

学习目标

  • 能区分认证、授权和资源归属。
  • 能设计 Token 生命周期和权限矩阵。
  • 能完成高风险操作审计。

实践验收

实现一个多项目系统，覆盖登录、刷新、退出、OWNER/MEMBER 角色、资源权限和审计日志。

  • 伪造资源 ID 无法越权访问。
  • 权限变化后旧 Token 和缓存不能继续访问。
  • 高风险操作有完整且脱敏的审计记录。

常见误区

  • 前端隐藏按钮就等于授权。
  • 使用管理员服务账号代表所有用户。
  • Token、密码和密钥进入日志。

全栈架构师视角

架构师要把权限从单个接口提升为统一模型。身份、角色、资源、动作和审计需要跨服务一致，否则系统越大越容易出现无法追踪的权限缺口。

为什么学

只要系统有业务状态，就会面对数据模型和查询问题。前端开发者进入全栈后，不能把数据库当作一个简单的 JSON 仓库。

实体、关系和约束

关系模型用表表达实体，用主键唯一标识记录，用外键表达引用。一对多、多对多和自关联要根据业务语义建模。规范化减少重复和更新异常，反规范化则用于明确性能取舍。

数据库约束是数据真实性的最后防线。唯一约束防止重复成员，外键维护引用完整性，非空和检查约束限制合法状态。删除规则必须根据业务决定限制、级联还是软删除。

  • 业务实体的唯一性交给数据库约束。
  • 删除策略要结合审计和恢复要求。
  • 不要用一张大表承载所有业务概念。
CREATE TABLE project_member (
  project_id uuid NOT NULL REFERENCES project(id),
  user_id uuid NOT NULL REFERENCES app_user(id),
  role text NOT NULL CHECK (role IN ('OWNER', 'MEMBER')),
  PRIMARY KEY (project_id, user_id)
);

SQL 查询、JOIN 和聚合

SELECT 负责投影，WHERE 在分组前过滤，GROUP BY 聚合，HAVING 在分组后过滤，ORDER BY 决定顺序，LIMIT/OFFSET 或游标负责分页。JOIN 会改变行数，必须理解连接条件和一对多关系。

窗口函数适合排名、分组内比较和最近记录。复杂报表不应全部拉到应用层处理，但也要避免一条 SQL 过度复杂无法维护。查询应返回业务真正需要的字段。

  • 分页排序字段要唯一，避免重复和漂移。
  • 区分 WHERE 和 HAVING。
  • 长查询要有执行计划和性能证据。

索引、事务和迁移

索引通过额外存储加速查询。联合索引遵循最左匹配，选择性、排序和回表决定效果。索引不是越多越好，写入成本、存储和统计信息都会受影响。EXPLAIN ANALYZE 能展示真实执行过程。

事务用开始、提交和回滚保证一组操作原子性。隔离级别决定并发读写看到什么数据，锁和唯一约束处理竞争。迁移必须与代码发布顺序兼容，避免旧代码遇到新结构立即失败。

  • 索引围绕真实慢查询建立。
  • 事务中避免慢网络调用。
  • 大表迁移考虑锁、回填和回滚。

学习目标

  • 能把业务实体转换成关系模型和约束。
  • 能编写 JOIN、聚合和窗口查询。
  • 能使用执行计划判断索引和事务效果。

实践验收

为项目、任务、成员和审计设计数据库结构，并实现统计查询、分页查询和并发事务测试。

  • 约束能阻止非法业务状态。
  • 关键查询使用合理索引并有执行计划。
  • 迁移能在新旧代码兼容窗口内执行。

常见误区

  • 只用应用层保证唯一性。
  • 在循环中对数据库发起 N+1 查询。
  • 为了性能随意冗余数据却没有同步策略。

全栈架构师视角

数据模型是最难回滚的架构决策。架构师需要关注数据所有权、一致性、访问模式、容量和迁移路径，而不是只关注当前 SQL 能不能运行。

为什么学

当用户在并发操作中看到丢失更新、重复数据或长时间等待时，问题通常已经超出语法层面，进入事务和容量设计。

ACID、隔离级别和并发异常

ACID 分别指原子性、一致性、隔离性和持久性。不同隔离级别允许不同并发现象，例如脏读、不可重复读和幻读。实际选择要在正确性和并发性能之间取舍。

并发更新需要乐观锁或悲观锁。版本字段、条件更新和唯一约束都能避免覆盖。事务边界应包含必须一起成功或失败的操作，但不应该包住慢外部调用。

  • 先说明业务一致性要求，再选择隔离和锁策略。
  • 用唯一约束处理并发重复创建。
  • 事务失败要能区分重试和不可恢复错误。
UPDATE task
SET status = 'DONE', version = version + 1
WHERE id = $1
  AND version = $2
  AND status = 'DOING'
RETURNING *;

查询性能和执行计划

慢查询可能来自缺少索引、返回字段过多、连接行数爆炸、排序、函数导致索引失效或统计信息过期。EXPLAIN ANALYZE 能显示扫描方式、预估行数、实际行数、循环次数和耗时。

优化顺序通常是减少数据量、改善访问路径、增加或调整索引、减少重复查询、缓存稳定结果。缓存不能替代错误数据模型，它只在正确查询基础上降低热点压力。

  • 先找真正慢的查询，再改索引。
  • 关注实际行数与预估行数偏差。
  • 写入性能和查询性能需要一起评估。

容量、分区和归档

数据量增长后，索引维护、备份恢复和查询扫描都会变贵。分区、归档、冷热分离和批量任务需要提前规划。大表删除和更新应分批执行，控制锁和复制延迟。

性能目标要结合业务 SLO。架构师需要知道峰值 QPS、数据增长、读写比例、延迟预算和恢复目标，才能决定扩容、分区和缓存策略。

  • 按时间和业务维度规划数据生命周期。
  • 批量变更分批提交并监控延迟。
  • 容量指标纳入日常监控。

学习目标

  • 能解释隔离级别和并发异常。
  • 能根据执行计划优化慢查询。
  • 能规划数据增长和归档策略。

实践验收

针对一个任务列表制造慢查询和并发更新问题，使用执行计划、索引和条件更新完成优化。

  • 并发更新不会覆盖他人数据。
  • 关键查询 P95 延迟达到目标。
  • 表增长和数据归档有可执行策略。

常见误区

  • 为了并发随意使用最高隔离级别。
  • 给所有字段加索引。
  • 缓存慢查询却不修正数据模型。

全栈架构师视角

事务和性能是架构取舍的核心。架构师需要把一致性要求、延迟预算、容量增长和恢复目标转换成数据库与缓存策略。

为什么学

缓存是性能工具，也是复杂来源。没有一致性策略的缓存会制造旧数据、权限泄漏和难以复现的生产问题。

缓存模式与失效

常见策略包括 Cache-Aside、Write-Through、Write-Behind 和读写缓存。缓存键必须包含租户、用户、资源、筛选条件、版本和语言等影响结果的变量。TTL 控制最大陈旧时间，主动失效处理业务写入。

缓存穿透是查询不存在的数据，缓存击穿是热点键失效，缓存雪崩是大量键同时过期。可以使用空值短缓存、互斥重建、随机 TTL 和热点预热缓解。

  • 缓存键不完整会导致跨用户、跨租户数据泄漏。
  • 缓存命中率必须和正确性一起观测。
  • 写入后明确删除还是更新缓存。
const key = `project:${tenantId}:${projectId}:v3`
const cached = await redis.get(key)
if (cached) return JSON.parse(cached)

const value = await repository.findProject(projectId)
await redis.set(key, JSON.stringify(value), "EX", 60)
return value

Redis、锁和故障降级

Redis 适合缓存、计数、限流、会话和短期运行状态。它不是所有数据的永久事实源。分布式锁需要拥有者标识、过期时间、续约和释放校验，锁失效后业务仍要保证幂等。

Redis 故障时，系统可以回退数据库、返回旧数据、限制功能或直接失败。选择哪种降级取决于业务风险。缓存服务不能成为单点，需要容量、持久化和高可用配置。

  • 锁不是分布式事务。
  • 所有缓存都明确 TTL 和可丢失边界。
  • 降级行为要在发布前演练。

NoSQL 和最终一致性

文档、键值、列式、全文检索和图数据库有不同访问模型。PostgreSQL 可以处理大量关系型和 JSON 场景；Redis 适合高速临时状态；Elasticsearch 适合搜索；对象存储适合大文件。

跨系统更新无法依赖单库事务，常见方案包括 Outbox、事件、补偿、对账和幂等消费。最终一致性要求业务能接受短暂延迟，并让用户看到明确状态。

  • 按访问模式选择数据库，不按流行度选择。
  • 跨系统写操作必须有补偿或对账。
  • 数据所有权和事实来源必须明确。

学习目标

  • 能设计缓存键、TTL 和失效策略。
  • 能识别缓存穿透、击穿和雪崩。
  • 能为跨系统更新设计最终一致性。

实践验收

为项目详情和任务列表设计缓存，并处理写入失效、缓存故障和跨服务数据同步。

  • 缓存不会泄漏跨租户数据。
  • 缓存故障时系统按预期降级。
  • 跨服务数据最终能对账并修复。

常见误区

  • 把 Redis 当作唯一数据库。
  • 缓存键忽略用户和权限。
  • 认为消息只会发送一次。

全栈架构师视角

架构师需要回答数据是否允许短暂过期、谁能接受旧值、系统故障时保留什么能力，以及跨系统不一致如何被发现和修复。

为什么学

用户要求导出报告、批量分析或实时查看进度时，同步接口和简单日志已经不足，必须进入任务系统和事件驱动设计。

任务队列和 Worker

提交接口只创建任务并快速返回任务 ID，Worker 异步执行。任务状态包含等待、运行、成功、失败、取消和重试次数。任务载荷应包含业务 ID 和版本，而不是过大的文件内容。

队列提供投递、重试和并发控制，但不自动保证业务只执行一次。Worker 可能在执行成功后崩溃、消息可能重复投递，因此任务必须幂等，并能从状态和结果中判断是否已完成。

  • 任务提交和任务执行分离。
  • 重试使用指数退避并设置上限。
  • 失败任务进入死信队列或人工处理区。
await queue.add(

SSE、WebSocket 和状态恢复

SSE 适合服务端向浏览器单向推送文本事件，例如任务进度和模型流式输出。WebSocket 适合双向实时通信。两者都需要心跳、重连、事件序号和过期状态处理。

客户端断线后不能假设服务端停止任务。恢复时先查询任务状态，再从最后确认的事件继续。推送事件应带任务 ID、序号和幂等标识，重复事件不会产生重复操作。

  • 实时连接有生命周期，任务状态独立保存。
  • 推送协议要定义事件类型和版本。
  • 断线恢复以持久状态为准。

可观测性和后端模块边界

一次请求可能经过网关、API、队列、Worker、数据库和第三方服务。correlation ID 串联所有日志和 Trace。指标需要覆盖延迟、错误、吞吐、队列深度、重试和任务成功率。

后端应按业务能力划分模块，路由负责协议，服务负责规则和事务，Repository 负责数据访问。抽象只在存在真实边界和复用价值时引入，不让简单调用链被多层包装隐藏。

  • 任务状态和失败原因可查询。
  • 慢任务、积压和死信有告警。
  • 关键链路能按 requestId 回放。

学习目标

  • 能设计任务状态机和幂等 Worker。
  • 能选择 SSE 或 WebSocket 并处理重连。
  • 能建立跨服务链路追踪和告警。

实践验收

实现一个报告生成系统，覆盖提交、队列、进度推送、取消、重试、结果下载和对账。

  • 重复消息不会生成重复结果。
  • 客户端重连后能看到正确进度。
  • 积压、失败和长时间运行都有可观测指标。

常见误区

  • 用 setTimeout 当生产任务队列。
  • 认为任务失败就自动重试到成功。
  • SSE 连接断开后把任务当成已取消。

全栈架构师视角

为什么学

容量、吞吐和延迟

容量设计从峰值流量、请求成本、数据库连接、缓存命中、队列积压和外部依赖限制开始。平均值不能代表高峰，P95/P99 延迟能暴露用户体验和资源竞争。

扩容应用实例通常最容易，但数据库连接和下游配额不会无限增加。需要为热门接口设计缓存、分页、批处理和限流，并测算每个扩缩容步骤的实际收益。

  • 容量预算包含应用、数据库、缓存、队列和第三方。
  • 慢依赖要有超时、熔断和降级。
  • 扩容策略不能放大数据库连接。

SLO、告警和故障域

SLO 用可观测指标表达服务目标，例如可用性、延迟和成功率。错误预算帮助团队判断何时优先修复稳定性，而不是不断增加功能。

故障域可能来自机房、可用区、数据库主节点、缓存、第三方服务或错误配置。高可用要求消除单点、验证故障切换，并避免一个实例故障演变成整个系统故障。

  • 告警对应明确的用户影响和处理动作。
  • 关键依赖准备超时、重试和降级。
  • 故障演练验证实际恢复时间。

备份、容灾和成本

RPO 表示允许丢失多少数据，RTO 表示允许停机多久。它们决定备份频率、复制方式、恢复工具和人员流程。对象存储、数据库配置和密钥都要纳入恢复范围。

成本来自计算、存储、网络、日志、模型调用和运维人力。架构师需要把性能、可靠性和成本放在同一张决策表中，明确哪些能力值得付费，哪些可以降级。

  • 备份恢复流程有责任人和演练记录。
  • 日志和指标有保留策略。
  • 成本与业务价值、SLO 一起评估。

学习目标

  • 能估算关键路径容量和限制。
  • 能定义 SLO、告警和降级策略。
  • 能设计备份、容灾和成本预算。

实践验收

为一个中型系统定义容量模型、SLO、依赖故障矩阵、RPO/RTO 和成本预算。

  • 容量假设有数据支持并有峰值余量。
  • 关键依赖故障时有明确降级行为。
  • 恢复演练证明 RPO 和 RTO 可达成。

常见误区

  • 只按平均值做容量估算。
  • 所有异常都变成高优先级告警。
  • 有备份但没有恢复过。

为什么学

生产系统中，安全问题是业务连续性和信任问题。一次越权、密钥泄漏或敏感数据外发可能造成的损失远超普通故障。

威胁建模和多层防护

威胁建模从资产、入口、信任边界和攻击路径出发。常见风险包括 XSS、CSRF、SQL 注入、SSRF、文件上传、越权、密钥泄漏和依赖漏洞。防护不能只依赖一个中间件。

输入校验、输出编码、参数化查询、最小权限、网络限制、Secret 管理和审计共同构成立体边界。内部服务也需要身份认证和授权，不能默认内网可信。

  • 每个入口都明确信任边界。
  • 危险能力默认关闭。
  • 安全事件有检测、隔离和恢复流程。

敏感数据、加密和合规

识别个人、项目、设备、位置和业务敏感数据，明确收集目的、存储位置、访问角色、保留期限和删除方式。传输和存储加密解决窃听风险，但不替代权限控制。

数据出境、第三方模型调用、日志保留和备份跨区域都需要合规评估。脱敏、最小化和访问审计是最常见的基础措施。

  • 敏感字段不进入日志、Prompt 和无必要缓存。
  • 密钥有轮换和吊销机制。
  • 删除和导出请求有明确流程。

供应链和自动化安全

依赖、构建工具、基础镜像、CI 凭证和发布脚本都属于供应链。需要锁定版本、扫描漏洞、限制构建权限、保护制品和验证发布来源。

AI Agent 的文档、工具结果和外部内容可能包含间接提示注入。模型不能直接决定权限边界，工具参数必须再次校验，高风险操作需要人工确认。

  • CI 令牌权限最小化。
  • 镜像和制品有来源校验。
  • Agent 只能调用白名单工具。

学习目标

  • 能按信任边界做威胁建模。
  • 能设计敏感数据生命周期和密钥策略。
  • 能建立依赖与 AI 工具安全边界。

实践验收

为一个全栈系统完成安全评审，覆盖 Web 漏洞、权限、依赖、Secret、日志、备份和 Agent 工具调用。

  • 所有外部输入都经过校验和权限检查。
  • 敏感数据在传输、存储和日志中有明确规则。
  • 关键依赖和高风险工具可审计、可撤销。

常见误区

  • 使用内部网络作为唯一安全边界。
  • 只做前端校验。
  • 将模型输出当作可信工具参数。

全栈架构师视角

安全是架构约束，不是上线前检查表。架构师需要在数据流、权限、依赖和自动化能力设计初期就把威胁模型纳入决策。

明确需求和关键路径

为什么学

从实现者走向架构师，第一步不是学更多框架，而是学会把模糊需求转换成清晰约束、边界和优先级。

从功能清单到业务不变量

需求文档常写“用户可以创建任务”，但架构师要进一步问：谁可以创建、任务属于谁、状态如何流转、失败能否恢复、删除后数据是否保留、并发创建是否允许。业务不变量是系统必须永远保持的规则。

例如项目必须至少有一个负责人、完成任务必须记录执行人、权限变更不能影响历史审计。这些规则应落实到数据库约束、服务逻辑、接口错误和测试中，而不是只出现在文档里。

  • 识别角色、资源、动作和状态。
  • 业务不变量必须能自动验证。
  • 需求编号与实现、测试建立追踪关系。

领域边界和统一语言

领域建模关注业务概念之间的关系，而不是数据库表数量。项目、任务、成员、审计、设备和报告都有各自生命周期。团队应该使用统一语言描述这些概念，避免接口、代码和产品文档各说一套。

边界划分应考虑变化频率、数据所有权、权限和团队职责。一个模块应能独立解释自己的规则，并只通过明确接口对外协作。

  • 模块边界围绕业务能力，而不是技术层。
  • 数据所有权明确。
  • 公共术语有稳定定义。

技术战略不是列技术栈，而是说明未来一段时间业务目标、关键能力、技术债、风险和投入顺序。例如先解决数据一致性还是先做多租户，先优化首屏还是先拆分服务。

演进路线应包含里程碑、可验证结果和退出条件。每一步都要能独立交付价值，不能把大规模重写作为唯一计划。

  • 技术目标与业务目标关联。
  • 每个阶段有可验证结果。
  • 旧系统有明确迁移和下线路径。

学习目标

  • 能从业务需求提取不变量和失败影响。
  • 能建立统一语言和领域边界。
  • 能制定分阶段技术演进路线。

  • 模块边界和数据所有权清晰。

为什么学

项目会不断出现技术选择。没有决策记录，团队会重复讨论、依赖个人记忆，甚至同时维护互相冲突的方案。

决策背景和候选方案

一个可执行的决策记录至少包含背景、约束、选项、结论和后果。比如选择 PostgreSQL 还是 MongoDB，应说明数据结构、查询模式、一致性、团队经验、运维能力和迁移成本，而不是只说“更适合”。

候选方案应控制在能真正执行的范围内。每个方案说明优势、代价、适用条件和不适用条件。架构师要从最小可行方案出发，避免提前设计所有未来。

  • 决策围绕明确问题，不围绕技术偏好。
  • 至少比较两个可实施方案。
  • 记录没有选择某方案的代价。
ADR-004：任务列表采用游标分页

背景：任务数量持续增长，OFFSET 分页出现性能和漂移。
决策：使用 created_at + id 作为游标。
代价：客户端不能随机跳页。
回退：保留兼容接口一个发布周期。

风险、可逆性和成本

高风险和不可逆决策需要更多验证。数据模型、公开接口、权限模型和跨团队协议一旦发布，回退成本较高。可以先通过小范围试点、影子流量、可兼容字段和迁移双写降低风险。

成本包括开发、运行、认知、迁移和机会成本。一个架构方案即使技术上先进，如果团队没有能力维护，也会长期增加故障和交付成本。

  • 区分可逆和不可逆决策。
  • 用试点和指标验证假设。
  • 复杂度必须换来明确收益。

记录后果和复盘

决策执行后要观察结果是否符合预期。如果指标没有改善，就更新或废弃方案，而不是维护错误的原判断。ADR 不是审批文件，而是未来团队理解上下文的工具。

复盘关注假设、数据和影响，不评价个人。失败决策也能提供边界信息，帮助团队改进评估方式。

  • 记录决策日期、负责人和状态。
  • 用业务指标验证结果。
  • 决策变化时更新而不是隐藏旧记录。

学习目标

  • 能写出背景清晰的 ADR。
  • 能识别可逆性、风险和成本。
  • 能用指标验证决策结果。

实践验收

为一个数据库、接口或前端框架选择撰写 ADR，并在一个迭代后根据数据复盘。

  • 决策能解释为什么不选其他方案。
  • 风险有缓解和回退计划。
  • 结果能通过指标或用户反馈验证。

常见误区

  • 结论先行，背景只写几句免责声明。
  • 把个人偏好写成架构原则。
  • 决策后从不验证假设。

全栈架构师视角

架构师的权威来自透明和可验证的取舍，而不是技术名词。好的决策让团队理解边界，也能在条件变化时安全调整。

为什么学

架构不是个人完成的静态设计，而是团队每天通过代码、流程和工具共同维护的系统。

把标准变成自动化

命名、格式化、提交信息、接口错误、权限规则和测试策略如果只靠口头约定，规模变大后一定会漂移。应把确定性规则放到格式工具、Lint、类型检查、Schema、生成器和 CI 中。

代码审查聚焦行为、权限、边界和风险。机械问题交给自动化，避免审查反复讨论空格和括号。

  • 能被脚本判断的规则自动化。
  • 自动化失败要能指出具体文件和原因。
  • 代码审查优先发现错误、回归和权限漏洞。

代码健康和技术债

技术债不是所有旧代码，而是会持续增加变更成本、故障风险或认知负担的问题。需要按影响范围、故障概率、修复成本和业务时机排序。

重构应小步进行，每一步保持可测试、可发布和可回退。不要等到系统无法维护时进行大爆炸式重写。

  • 技术债和业务目标关联。
  • 重构过程保持主分支可发布。
  • 删除旧路径有明确时间和负责人。

知识恢复与持续交付

架构文档应描述当前事实、关键边界、请求链路、数据流和运行方式。ADR 记录为什么这样选。README 记录如何启动、测试和部署。文档必须随代码更新，不能长期失真。

持续交付依赖小批量变更、快速反馈、自动化验证和可观测发布。团队需要能独立发现、定位、回滚和恢复问题。

  • 新人能根据文档恢复项目上下文。
  • 关键模块有负责人和运维手册。
  • 每次发布都能观察业务和技术指标。

学习目标

  • 能把工程规范转化为自动化门禁。
  • 能排序并渐进偿还技术债。
  • 能建立文档、复盘和持续交付机制。

实践验收

为一个团队设计工程规范、质量门禁、文档体系、技术债台账和发布复盘流程。

  • 新成员能按文档完成首次交付。
  • 质量规则由工具持续执行。
  • 技术债有优先级、负责人和退出标准。

常见误区

  • 规范只写在文档，没有工具执行。
  • 把所有重构都当成技术债。
  • 架构文档和真实代码长期不一致。

全栈架构师视角

真正成熟的架构师不只设计系统，还设计团队如何理解、修改、发布和恢复系统。可维护性、知识和自动化是架构能力的一部分。
